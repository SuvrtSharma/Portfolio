Most AI developer tools work the same way: hand the model your code, let it
tell you what's wrong. It's fast to build and it demos well. It also means every
number on the screen might be invented.

When I started building **Arqon**, a visual architecture tool for SQL Server
stored procedures, I made one rule before writing any code: **the LLM is not
allowed to state facts.**

## The pipeline

Every analysis in Arqon flows one way:

```
Facts → Analyzer Engine → Structured Context → LLM → Human Explanation
```

The analyzer is plain, deterministic C#. It parses T-SQL with ScriptDom, builds
the control-flow graph, resolves dependencies, runs the detectors, and computes
the architecture score. Given the same SQL, it produces byte-identical output,
and I treat any non-determinism as a bug, enforced by golden tests.

Only *after* all of that does a model get involved, and its job is narrow: take
the structured findings and explain them in plain English. It never originates a
number, a finding, or the reason behind a recommendation.

## Why be this strict

Because a wrong explanation should always be debuggable. With this boundary, a
bad answer has exactly two possible causes:

- **Bad facts**: a bug in the analyzer, which a test can pin down.
- **Bad prose**: a prompt problem, which I can see because the exact context
  sent to the model is retained.

What it can never be is an opaque hallucination that nobody can trace.

There's a side effect I didn't expect: the constraint pushes real logic *into*
the engine. If a feature feels "AI-native" (scoring, advice), it has to be
expressible as deterministic analysis first. And when the model is unavailable,
Arqon still works. You get every fact and diagram, just without the prose.

## The hard case: AI-generated fixes

Explanations are easy to fence. Suggested *fixes* are not. A rewrite isn't
commentary. It's code someone might paste into production, and it is
generated by definition.

So the engine checks the AI's work. Arqon already owns a deterministic detector
suite that maps SQL to findings. When the model proposes a rewrite, the engine
runs those same detectors on it and reports a verdict that the model has no say
in:

- **resolved**: the finding fired on the original snippet and not on the rewrite
- **stillDetected**: the rewrite didn't fix it
- **doesNotParse**: the rewrite isn't valid T-SQL
- **notVerifiable**: the original snippet can't be checked in isolation, and
  the UI says so honestly instead of upgrading it

And the fix is never applied automatically. Arqon shows it as a labelled
suggestion with its verdict and a Copy button. Changing your code stays a
deliberate human act.

One nuance matters a lot: **resolved** is a fact about Arqon's detectors, not a
promise that the rewrite means the same thing as the original. The UI wording
has to keep that distinction, or the whole trust model leaks.

## The takeaway

If you're adding AI to a tool people rely on, decide early which side of the
line every claim on screen lives on. The model is a very good narrator. Let
something deterministic be the source of truth, and wherever you can, let that
same deterministic layer grade the model's homework.
